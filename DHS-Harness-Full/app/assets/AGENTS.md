# 你运行在一台 Android 手机上

这个工作区不是普通电脑 —— 你宿主在一台真实的 Android 设备上（应用包名 `com.dsh.harness`），
并且**你可以操控它**：打开应用、发通知、读写剪贴板、震动、分享、查机型电量。

这些能力通过一个**本地 HTTP 控制桥**暴露。桥只监听 `127.0.0.1`，不出网，也不接受外部连接。

## 第一步永远是这个

```sh
curl -s -H "X-DSH-Token: $DSH_ANDROID_BRIDGE_TOKEN" "$DSH_ANDROID_BRIDGE_URL/help"
```

它会返回**当前可用的全部端点**（比我在这里列的可能更新）。先跑它，再决定用什么。

两个环境变量在启动时自动注入：

| 变量 | 含义 |
|---|---|
| `DSH_ANDROID_BRIDGE_URL` | 形如 `http://127.0.0.1:3099/` |
| `DSH_ANDROID_BRIDGE_TOKEN` | 必需，放进 `X-DSH-Token` 请求头 |

**每个请求都必须带这个头**，否则返回 401。

> 如果这两个变量取不到（不同部署方式下环境注入位置可能不同），
> 可以从宿主进程读：`grep -al 'DSH_ANDROID_BRIDGE_URL=' /proc/[0-9]*/environ`。

## 打开手机上的应用

**`/device/open` 需要的是包名，不是应用名。** 包名不能靠猜 —— 用 `/device/apps` 查：

```sh
# 1. 按名称搜，拿到包名
curl -s -H "X-DSH-Token: $DSH_ANDROID_BRIDGE_TOKEN" \
     "$DSH_ANDROID_BRIDGE_URL/device/apps?q=微信"

# 返回： {"count":1,"apps":[{"package":"com.tencent.mm","label":"微信"}]}

# 2. 用包名打开
curl -s -X POST -H "X-DSH-Token: $DSH_ANDROID_BRIDGE_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"package":"com.tencent.mm"}' \
     "$DSH_ANDROID_BRIDGE_URL/device/open"
```

不带 `q` 就列出全部已安装应用（可能有上百条，建议先搜）。

也可以直接开链接，不需要包名：`-d '{"url":"https://example.com"}'`

## 其余常用能力

| 端点 | 用途 |
|---|---|
| `POST /device/notify` | 发系统通知 `{"title":"…","text":"…"}` |
| `POST /device/toast` | 屏幕上一闪而过的轻提示 `{"text":"…"}` |
| `GET`/`POST /device/clipboard` | 读 / 写剪贴板 `{"text":"…"}` |
| `POST /device/vibrate` | 震动 `{"ms":240}` |
| `POST /device/share` | 调起系统分享 `{"text":"…"}` |
| `GET /device/info` | 机型 / 系统版本 / 工作区路径 |
| `GET /device/battery` | 电量与充电状态 |
| `GET /fs/list?path=<dir>` | 列目录（省略 path 则为工作区） |
| `POST /ui/status` | 把工作状态显示到通知栏（并尽力上岛） |

## 主动通知：你和用户之间唯一的主动通道

**用户在手机上同时开着别的应用，不会一直盯着这个界面。**

这句话决定了下面这条规则的分量：**卡在"等用户回应"上的任务，如果没有通知，就会永远卡住。**

所以以下四种时刻，**必须**发通知（`POST /ui/status`，`mode` 用默认的 `auto`）：

| # | 时刻 | 为什么必须发 |
|---|---|---|
| **1** | **任务完成** | 用户想知道结果，不想打开应用才看到 |
| **2** | **需要用户决策 / 授权 / 给权限** | ⚠️ **最容易卡死**：你在等一个永远不会来的答复 |
| **3** | **遇到错误或阻塞，做不下去了** | 不要静默停住；让用户知道要介入 |
| **4** | **长任务开始** | 让用户对等待时间有预期 |

**其中第 2 条最重要。** 一旦发现自己需要用户做点什么 —— 确认一个操作、授予权限、
回答一个问题 —— **先发通知，再去等**。

```sh
-d '{"title":"任务完成","text":"重构了 3 个文件，测试全过","chip":"完成"}'
-d '{"title":"需要你确认","text":"即将删除 build/ 目录，回复\"确认\"继续","chip":"待确认"}'
-d '{"title":"任务受阻","text":"缺少存储权限，请在设置里授予后告诉我","chip":"受阻"}'
-d '{"title":"开始构建","text":"预计需要几分钟，完成后会通知你","chip":"构建中"}'
```

**文案要求**：

- `title` —— 短，一眼看出是**什么事**
- `text` —— **一句话给出关键信息**，用户扫一眼就懂，别写实现细节
- `chip` —— **2–4 个字**（`完成`、`待确认`、`受阻`、`构建中`）

**什么时候不要推**：在耗时阶段开始时推一次就够。
❌ 不要每条命令都推（会把通知刷爆，用户反而会关掉它）；❌ 不要推与当前任务无关的内容。

## /ui/status 的实际效果：因手机厂商而异

**重要：不要向用户承诺"灵动岛会出现"。**

`POST /ui/status` 做两件事：

1. **一定**更新通知栏里的常驻通知 —— **所有 Android 设备都支持，这条是可靠的**
2. **尽力**把状态升级成"实时活动" —— 状态栏芯片、锁屏卡片、以及各厂商的"岛"

**第 2 步因厂商而异，而且通常有授权门槛：**

| 平台 | 该能力的名称 | 是否需要单独申请 |
|---|---|---|
| 小米 / 澎湃 OS | 超级岛 · 焦点通知 | **需要**（开发者平台：企业认证 + 审核 + 设备白名单） |
| Android 16+ 原生 | Live Updates | 声明权限，且用户需在设置中开启 |
| 其他厂商 | 各自的实现 | 多数同样需要申请 |

**所以判断推送是否成功的标准是「通知栏那条常驻通知的文案变了」，而不是「岛有没有出现」。**

如果返回里带 `islandCapability` 字段，那是**能力线索**（系统属性 / 协议版本），
**不等于已获授权** —— 授权状态没有公开查询接口。

**用户问"为什么灵动岛没反应"时，如实回答**：
这取决于手机厂商是否给本应用开放了该能力，需要开发者侧申请，**不是应用没实现**；
同时告诉他状态在**通知栏**是正常显示的。

`mode` 参数：`auto`（默认，双通道，最稳）、`normal`（只发通知栏）、`focus`（只发岛）。
**未确认设备已授权前不要用 `focus`** —— 那会让状态完全不可见。

## 关于这类设备的一些通用事实

- **存储**：工作区通常在公共存储（`/storage/emulated/0/…`），文件管理器里能看到；
  应用私有目录在 `/data/user/0/com.dsh.harness/files/`（部分设备可能是 `/data/data/…`，
  两者等价）。**私有目录之外的地方你读写不了。**
- **没有 root**，也没有 `am` / `pm` 之类的系统命令 —— 想操作 Android 就走这座桥。
- **shell 环境是裁剪过的 Termux**：常用命令未必齐全，不要假设 `apt` / `pkg` 能用；
  缺什么用 Node 或桥替代。
- **控制设备是有副作用的操作**：打开应用会把用户界面切走。除非用户要求，
  不要主动去开应用或震动手机。
- **不确定设备能力时，先查再动**：`GET /device/info` 给出厂商与系统版本，
  `GET /help` 给出当前实际可用的端点。**不要假设某个端点一定存在。**
